# H2: how it behaves, measured

> Written in the 2026-11 docs cleanup from `docs/H2_BACKEND.md` (the H2 backend design and its step logs,
> 2026-07-31 to 2026-08-01), which it replaces. Sections keep their old numbers, because code and the probe
> write-ups in [probes/](probes/) cite them ("§4", "§9"); a gap is a section that was cut. Full original:
> `git show de2745351:docs/H2_BACKEND.md`. The index of this folder, and how each database was measured, is
> [README.md](README.md).

**Where H2 stands today (verified in the tree, 2026-11).** Two H2 versions are in play. The product's H2 is
**2.1.214** (`tools/deps/jars_table.bzl`, the engine's own version, and the target of its golden SQL); the PCT
lane (gate 7, `//pct:pct_h2`, the Relation suite only) runs on **2.4.240** (`h2_modern`, test-only, never beside
2.1.214 on one classpath). The H2 dialect writes executable 2.1.214 SQL; its 2.3+ profile `H2Modern` is chosen by
the connected server's version (`forServer`: 2.1 and 2.2 keep H2's walls). Since 2026-11-03 both are rendered by
the Rust library (`rust/lite-dialect/src/h2.rs`), whose header states the dialect's shape: native QUALIFY, no
LATERAL (the collection carrier rides JSON), no typed-JSON navigation on 2.1.

**Evidence standard.** The capability map was produced by **executing ~200 probe statements against
a real `h2-2.1.214.jar`** with the engine's own connection settings, cross-checked against the
version-exact function catalog in `org/h2/res/help.csv` inside that jar. The golden-text gap was
produced by **instrumenting and running the full corpus sweep twice**. Where documentation and
execution disagreed, execution won. Claims sourced any other way are marked.

## 1. Verdict

**Achievable, and the blocker is not what anyone expected.**

- **SQL-side graph emission is *not* the obstacle.** It was predicted to be, twice, and refuted both
  times — the second time by running legend-lite's exact envelope shape on H2 and getting correct
  nested JSON in one statement. Graph fetch is a **rendering override plus one small rewrite pass**.
- **The wall is `LATERAL`**, which no H2 version has — not 2.1.214, not 2.3.232 (nor 2.4.240, per the
  addendum).
- **The wall is really about the collection carrier, not the graph.** See §4.
- **Minimum viable scope is 206 of 256 constructs — 80%** — and it includes the *complete* nested
  object-graph path.
- **Golden-text compatibility is a separate and much weaker proposition.** 25.7% of golden asserts
  already matched byte-for-byte; of the divergences, **66% are query *shape*, not spelling**, and the
  total achievable by normalization is ~6%. Recommendation in §6: binding for a defined subset only.

## 2. Buckets, and what H2 does natively

Buckets (used by every probe write-up in [probes/](probes/)): **A** native · **B** MIR rewrite pass ·
**C** rendering override only · **D** structurally impossible on H2.

> Cut in the 2026-11 docs cleanup: the 256-construct capability-count table and its `SqlFn`-count correction
> (2026-07-31). The current per-dialect decisions are generated in `docs/dialect-capability/` (H2 is not one of
> its dialects; this file carries H2's measured spellings). Full text: `git show de2745351:docs/H2_BACKEND.md`.

**Notable A's, verified by execution (2.1.214):** correlated scalar subqueries nested ≥3 deep including inside
`JSON_OBJECT`; all window frame kinds including `RANGE BETWEEN INTERVAL '1' DAY PRECEDING`; **native
`QUALIFY`** (H2 has it — `QualifyToSubselect` becomes a free fallback rather than a requirement); all
30 aggregate/window functions with `DISTINCT` and in-aggregate `ORDER BY`.

**Notable C's:** H2 has **no bitwise operators at all** (`1 << 2` is a syntax error) — `BITAND`/`BITOR`/
`LSHIFT` etc. instead; 12 temporal functions map through `EXTRACT`/`DATEDIFF`/`DATEADD`/`FORMATDATETIME`;
`ROUND_EVEN` has no H2 equivalent (H2's `ROUND` is HALF_UP — `2.5→3`, `3.5→4`, measured).

**Spellings probed on the real 2.1.214 jar while the dialect was built (2026-08-01):**

| DuckDB | H2 |
|---|---|
| `rowid` (the physical row order, e.g. a `STRING_AGG` determinism key) | `_ROWID_` |
| `d + to_days(n)` (fails on H2 everywhere a date shifts) | `dateadd(UNIT, n, d)` |
| `date_part` (H2 has none) | `extract(UNIT FROM x)` |
| `starts_with` | `LEFT`/`CHAR_LENGTH` equality (no LIKE-escape hazard; probed with `%` in the prefix) |
| `quantile_cont(v, q)` | `PERCENTILE_CONT(q) WITHIN GROUP (ORDER BY v)` |
| `json_object('k', v)` / `json_group_array` | `JSON_OBJECT('k': v)` / `COALESCE(JSON_ARRAYAGG(v ORDER BY …), JSON '[]')` (§3) |

**Measured traps (2.1.214, the engine's connection settings):**

- `//` is a **line comment** in H2: `SELECT 7 // 2` returns **7**, silently, no error. Integer division
  must render `a / b`.
- `GREATEST`/`LEAST` **skip** NULLs; `ROUND` is HALF_UP, not banker's; `JSON` equality is textual and
  key-order-sensitive.
- DuckDB's `starts_with`, `ends_with`, `strpos`, `regexp_full_match`, `to_base64`, `from_base64` and `to_days`
  do not exist on H2 (`[90022] Function not found`).
- The JDBC driver hands back `BOOLEAN` as H2's BIT → `Integer` where DuckDB gives `Boolean`, and `JSON` as
  `byte[]` (§3); `DECIMAL` scale and arrays/structs also need a `normalize` row.

## 3. The graph layer is not the blocker — verified by execution

This shape, taken from today's Java `Lowerer` (`Lowerer.java:627` and `:737` at the time), **ran on H2
2.1.214 and returned correct nested JSON in one statement, no round trips**:

```sql
SELECT COALESCE(JSON_ARRAYAGG(JSON_OBJECT(
  'name': s.name,
  'dept':     (SELECT JSON_ARRAYAGG(JSON_OBJECT('name': d.name)) FROM dept d WHERE d.id = s.dept_id),
  'projects': (SELECT COALESCE(JSON_ARRAYAGG(JSON_OBJECT('name': p.name)), JSON '[]')
               FROM proj p WHERE p.emp_id = s.id)
) ORDER BY s.id), JSON '[]') AS result FROM emp s;
```

Also verified: three-level nesting; nested JSON stays JSON rather than becoming a quoted string;
ordered aggregation with `DESC` and `NULLS LAST`; date/timestamp/decimal/boolean leaves.

**Three deltas, all rendering:**

| | DuckDB | H2 |
|---|---|---|
| Object constructor | `json_object('k', v, …)` — positional pairs | `JSON_OBJECT('k': v, …)` — **the positional form is a syntax error** |
| Array aggregate | `coalesce(json_group_array(x),'[]')` | `COALESCE(JSON_ARRAYAGG(x … NULL ON NULL), JSON '[]')` — **H2 defaults to `ABSENT ON NULL`; DuckDB keeps nulls.** Must be explicit |
| Read-back | driver returns a JSON node | H2 maps `JSON` to **`byte[]`**, so a plain `String.valueOf(rs.getObject(1))` yields `[B@1f3a` (canonicalized to the UTF-8 string in the dialect's `normalize` since 2026-08-01) |

**And `CheckedEnvelope` turns out to be a rewrite, not a wall.** The checked graph-fetch envelope builds
`TO_VARIANT(LIST_FILTER(ARRAY[case1, case2, …], x -> x IS NOT NULL))` over a **statically sized**
array — one `CASE` per constraint. H2's `JSON_ARRAY(… ABSENT ON NULL)` drops NULL elements, which is
that `list_filter` exactly, with no lambda:

```sql
SELECT JSON_ARRAY(CASE WHEN 1=0 THEN JSON_OBJECT('id':'c1') END,
                  JSON_OBJECT('id':'c2'), ABSENT ON NULL)   -->  [{"id":"c2"}]
```

One `SqlRewriter` pass keyed on `LIST_FILTER(ArrayLit, Lambda(x, IS_NOT_NULL(x)))`. **Bucket B.**

### 3.1 And legend-lite's approach is *less* demanding of the backend than the engine's

legend-lite's graph fetch needs **read-only `SELECT`**. The engine's needs DDL rights at query time,
a session temp namespace, connection-scoped drop hooks, a JVM hash map holding every parent object of
the batch — and for H2 specifically it **spools parent primary keys out of the JVM to a CSV file on
disk, then `INSERT INTO temp SELECT * FROM CSVREAD('<path>')`**
(`§/graphFetch/relationalGraphFetch.pure:283-289`).

That is why the engine gates temp-table graph fetch to **2 of 21 backends** (`:108-114`) and ships
`throw new UnsupportedOperationException("not yet implemented")` for BigQuery, Databricks and Trino.
Do **not** adopt it as an escape hatch (it computes in the JVM what the database should). Borrow only its
*taxonomy*: graph fetch has three legitimate shapes (SQL-assembled, temp-table-joined, IN-list-joined) and a
backend's capabilities select one.

**The real cost, honestly:** N nested correlated scalar subqueries have a depth-scaling planner
cost that N flat queries plus a host join do not. That is a **performance** ceiling to measure, not a
correctness objection.

## 4. The real wall — and what it is actually about

### D1 — no `LATERAL`, no correlated table function. Unfixable.

`LATERAL` is not a keyword in H2 2.1.214 **or 2.3.232** (nor 2.4.240, per the addendum) — the parser reports
`Function "LATERAL" not found`, and the upstream issue is still open. Every correlated FROM form
fails: `t, UNNEST(t.a)`, `CROSS JOIN UNNEST`, `JOIN UNNEST … ON TRUE`, `t, TABLE(v INT = t.a)`,
`t, SYSTEM_RANGE(1, t.n)`, even `t, (SELECT t.a)`.

**Kills** (in the IR's vocabulary): `UNNEST`, `CROSS_LATERAL`, `LEFT_LATERAL`, the whole 16-member `LIST_*` value
family, `LIST_FLATTEN`, `RANGE_FN`, `VARIANT_ELEMENTS`.

**Real carve-out:** where the array is **not row-correlated** — a literal collection, a FROM-less
scalar root — select-list `UNNEST` rewrites to FROM-clause `UNNEST`, which H2
has. `FROM UNNEST(ARRAY[1,2], ARRAY['a','b']) AS t(c1,c2)` even zips multiple arrays, matching a
parallel select-list unnest. **So D1 is *correlated* explosion, not all explosion.**

### The other D's, ranked

| | Gap | Scope | Note |
|---|---|---|---|
| **D2** | No JSON navigation (2.1.214) | `VARIANT_GET`, `VARIANT_ELEMENTS`, `JSON_TYPE`, `JSON_MERGE_PATCH` | **Mostly fixable by version bump** — the study read H2 2.2.220+ as adding `(json).field` / `json[i]`; today's code treats 2.3+ as the navigating profile (`(x)."key"`, `(x)[i]`; the note under the addendum) and keeps 2.1/2.2's walls. `JSON_TABLE` never exists, so `VARIANT_ELEMENTS` stays D |
| **D3** | No lambdas, any version | every `SqlExpr.Lambda`, the fold strategies, `LIST_FILTER` | Standard lambda-free encoding needs `UNNEST` + re-`ARRAY_AGG` → blocked by D1 |
| **D4** | `SourceUrl` | 1 site | `data:` needs JSON→rows (D2); `file:` needs a JSON reader (H2 has CSVREAD only) |
| **D5** | No `MAP` type | 7 SqlFns, 3 type sites | Re-encoding as parallel arrays or JSON re-enters D1/D2 |
| **D6** | No `TYPEOF` | the JSON date wrap on every Pure `Date` graph leaf | **Soft — downgradeable to C.** The dispatch is runtime because "setup DDL can diverge from the store declaration", but on H2 the column type is statically known from `INFORMATION_SCHEMA` |
| **D7** | Dynamic `PIVOT` | empty-`in` form | Static `in`-pinned form is **B** (conditional aggregation) |
| **D8** | Missing functions | `SPLIT`, `REVERSE_STRING`, `LEVENSHTEIN`, `JARO_WINKLER`, `REGEXP_EXTRACT_ALL`, base64 ×2 | Absent from every H2 version; pure-SQL constructions need correlated `SYSTEM_RANGE` (D1) |

### 4.1 The redesign, if you want the last 19%: it is the collection carrier

**Not the graph layer.** In 2026-07 a Pure `List<T>` became a SQL array and every operation on it a DuckDB
list lambda; of 122 `LIST_*` emission sites, 110 were the PCT collection-function surface, and graph fetch
touched `LIST_FILTER` at exactly one place.

Reaching H2 means lowering collections to **relations** — a correlated derived table joined on a
synthetic key, or an ordinal-keyed side table — so that `filter`/`map`/`fold`/`exists` become
`WHERE`/`SELECT`/window/`EXISTS` over rows rather than lambdas over an array value. That is a
lowering redesign, not a dialect exercise.

**And it is the right redesign for N backends generally**, since Postgres, Snowflake and BigQuery
each need a *different* one of unnest-lateral / array functions / lambdas. H2 is simply the backend
that forces the question.

> **Since then:** the carrier was redesigned (`docs/CARRIER_REDESIGN.md`, the per-dialect carrier
> strategies); on H2 the collection carrier rides JSON (`rust/lite-dialect/src/h2.rs`). On the 2026-08-01 full
> H2 sweep the carrier walls were exactly sized: 1,249 tests refused, UNNEST 792 + array-literal 226 +
> LIST_AGG 133 + LIST_CONTAINS 30 + LIST_GET 20 + TYPEOF 17 + toVariant 8 + LIST_BOOL_AND 5 + struct 5 +
> banker's ROUND 4 + tail 9 (703/2,538 passing then).

### 4.2 Do not take the `CREATE ALIAS` exit

H2's `CREATE ALIAS` is **enabled by default** in 2.1.214 (verified — both a `FOR "java.lang.Math.abs"`
alias and an inline-source alias were created and called). It would close every remaining D — by
running Java **inside the database process**, requiring DDL rights on the target, and opening
remote-code-execution surface (`h2.allowedClasses` defaults to `*`).

That is the execution tenet inverted, not satisfied. The engine does exactly this — 15 UDFs, §7 — and roughly a
dozen of its H2 function spellings *are* those UDFs rather than H2 SQL.

## 6. Golden text: the contract is rows, not SQL text

> Cut in the 2026-11 docs cleanup: §5 (five defects of the 2026-07 Java renderer, since fixed; its measured H2
> facts are in §2) and §6's census tables (2026-07-31: 1,454 golden asserts, 373 byte-exact). Full text:
> `git show de2745351:docs/H2_BACKEND.md`.

**Upstream's mechanism is exact string equality.** `assertSameSQL` (`tests/testAssert.pure:18`) is a bare
`assertEquals` after `sqlRemoveFormatting` (`helperFunctions.pure:58`), which is
`$sql->replace('\n','')->replace('\t','')` — it **deletes** newlines and tabs. It does not collapse runs of
spaces, trim, case-fold, or touch quoting. **Spaces are significant.** Nothing in either upstream repository
parses two SQL strings and compares structurally. Of the engine's 2,687 relational `test.Test` functions,
1,581 (58.8%) contain at least one golden-SQL assertion, and the golden corpus is essentially all H2.

**What was measured (2026-07-31):** two thirds of the divergences were query *shape*, not spelling (the largest
class: the engine's semi-join, `left join (select distinct …) … is not null`, where lite writes a correlated
`EXISTS`); normalizing both sides for casing, quoting and alias identity made 1 of 372 records equal, and erasing
every output alias only 23 (6.2%), which is destructive, since aliases are the TDS column names.

**Three reasons golden text is not binding corpus-wide:**

- **Matching would make execution worse.** The golden semi-join re-scans and re-joins the root table inside a
  subquery to compute emptiness, then materializes a `DISTINCT` over it: strictly more work than a correlated
  anti-join on both DuckDB and H2.
- **Most diverging tests compare against a host-assembly query**: class-root goldens, a flat
  `select "root".ID as "pk_0", …` rectangle that the engine's Java then assembles into objects. Converging means
  computing in the host or shipping two lowerings.
- **At least one golden is provably wrong.** `testExistsWithAttributesFromLeftInAndCondition`
  (`functions/tests/testExists.pure:410-417`): the Pure source reads `$p.name` from the **outer** person; the
  engine's decorrelation into `select distinct` rebound it to the **inner** employee. Rows coincide on the seed
  data so both pass, but making the golden pass would require reproducing an engine bug. `…InOrCondition` at
  `:419` is the same shape. A binding contract must be able to say "this golden is wrong".

**The recommendation (2026-07-31):** row equality stays the contract; pin the goldens that already match so they
cannot silently regress; keep spelling differences (a burndown list) apart from shape differences (an architecture
decision to make explicitly).

## 7. Connection and configuration — "H2 compatible" does not mean stock H2

**The engine forks H2's source.** Its `h2-execution-2.1.214` module shades the upstream jar while
*excluding* two classes it then supplies itself, each carrying `@legend-fix` comments:

- `org/h2/engine/Mode.java:509-510` — `mode.charPadding = CharPadding.NEVER`
- `org/h2/value/TypeInfo.java:1000, 1011` — allow numeric↔boolean and varchar↔boolean comparisons

Without the first, `CHAR(n)` pads and string comparisons diverge from the goldens. Without the
second, the corpus's numeric↔boolean comparisons throw. **Decide this explicitly — either shade a
patched H2 at test scope, or accept a named exclusion set — but do not discover it as mysterious row
divergence.** (Measured later: the forked H2 also tolerates duplicate column names in derived tables where
stock 2.1.214 rejects them, "Duplicate column name".)

**Plus `MODE=LEGACY` and a 26-word `NON_KEYWORDS` list**, and **15 Java UDFs installed on every
connection** (`CREATE ALIAS legend_h2_extension_*`: `json_navigate`, base64, `hash_md5/sha1/sha256`,
`flatten_array`, `split_part`, `edit_distance`, `jaro_winkler_similarity`, `convertTimeZone`,
`lpad`/`rpad`). Roughly a dozen of the engine's H2 function spellings are those UDFs. Every engine H2 session
also opens with `DEFAULT_NULL_ORDERING=HIGH` (found at the legend-engine 4.145.0 bump, 2026-09-12;
`docs/GATES.md`, batch 8).

**Three concrete deltas for legend-lite:**

- **Add `OVER` to `NON_KEYWORDS`.** The corpus path (legend-pure `TestDatabaseConnect.java:107-126`)
  omits it; the engine's *execution* path (`H2Manager.java:69`) includes it; and `over` is a reserved word
  requiring quoting.
- **Pin `timeZone = 'GMT'`.** `relationalSetUp.pure:1242-1248` hard-codes it and every temporal
  expectation in the corpus depends on it.
- **Adopt quote-if-needed.** The engine leaves `DATABASE_TO_UPPER` at its default (true); a harness that
  quotes **every** column must instead set `DATABASE_TO_UPPER=false;CASE_INSENSITIVE_IDENTIFIERS=TRUE`.
  Driving quoting from the parser's record of whether a column was quoted would let legend-lite run the
  engine's exact connection string. **Watch the collision:** on DuckDB the raw-SQL boundary quotes for the
  *opposite* reason. Two backends want opposite policies from one boundary.

## 9. The declared-gap registry — copy this

The engine solved a problem legend-lite has. `SqlDialect.expectedSqlDialectTestErrors:
Map<String,String>` (`sqlDialect.pure:38`, H2's populated at `h2SqlDialect.pure:74-118`) plus JSON
manifests `pct-manifests/relational-<db>/<Scope>_manifest.json` of shape
`{"test":…, "expectedError":…}`. **H2 has 512 entries**; 6,717 across all dialects (legend-engine at the time
of writing, 2026-07-31).

The semantics are what matter:

> A named error the manifest **expects** is a **passing** test. A named error whose **text changed**
> is a **failure**. An **unexpected pass** is *also* a failure.

That is the difference between a burndown ledger and a skip list, and it is the only way honest
capability refusals (§4) stay legible across a multi-backend matrix. legend-lite adopted it: every PCT lane
pins each failing test by its message (`Test_LegendLite_<Lane>_<Suite>Functions_PCT`), and on H2 a registry of
corpus replay declines is asserted on every full sweep (duplicate column name ≤ 10, the engine's plan-level
`tempTableForIn` ≤ 6, `legend_h2_extension_` UDFs ≤ 1: growth fails the build, shrink prints a retire hint;
2026-08-01).

## 10. Two outcomes, not one soft bucket

- **`UNSUPPORTED` and `FAIL` are distinct.** `UNSUPPORTED` = the renderer threw a capability wall
  (`DialectCapability`, typed, classified by type and never by message; honest, expected, §9-registered).
  `FAIL` = the database executed and produced wrong rows. A test that passes on DuckDB and fails on H2 is a
  **FAIL in the H2 row**, and must not touch the DuckDB baseline.
- **`SHAPE` stays one-dimensional.** It is a property of the test body, not the backend; giving it a backend
  axis doubles the denominator dishonestly.

## 12. The build order, as landed (all 13 steps by 2026-08-01)

Code cites these steps by number (`CsvSeed`, the referee's `RefereeVerify`):

1. The silent wrong-answer and invalid-SQL fixes (integer division written `//`, a comment on H2; the engine-text
   printer's DuckDB spellings, unrenamed star alias and precedence-dropping `AND`; invalid DDL for quoted columns).
2. Seeding emits `DROP TABLE IF EXISTS` + `CREATE TABLE` instead of `CREATE OR REPLACE TABLE` (the cause of ~39
   H2 replay declines).
3. The replay oracle compares by declared SQL type: a blanket `MathContext(10)` collapsed values at 11
   significant digits on both sides, so two values agreeing in their first 10 digits compared equal (a silent
   false pass, epoch-millis inside the blast radius).
4. Every silent replay decline is counted.
5. Milestone 1: legend-lite's own SQL executed on H2 with rows compared to DuckDB's (first sweep: 289 verified,
   0 diverged, 135 unverifiable).
6. Bump H2 off 2.1.214 (weakened by the addendum: the product stays on 2.1.214, the PCT lane runs 2.4.240; top
   of this file).
7. H2 at compile scope beside DuckDB and SQLite.
8. An H2 execution dialect beside the engine-text printer `EngineStyleH2`, never `EngineStyleH2` itself (its
   output is byte-pinned to goldens).
9. Typed capability walls and the measured capability budget (§10).
10. Dialect and connection bound together at one execution seam (the live connection's product name picks the
    dialect; a mismatched declared type is refused loudly).
11. The first `normalize` codec rows (JSON as `byte[]`).
12. The corpus's raw H2 statements run verbatim on the H2 target (translated only for DuckDB).
13. The declared-gap registry (§9).

## 13. What NOT to do

- **Don't adopt the engine's temp-table graph fetch** as a fallback (§3.1). Its prerequisites are strictly
  harder than `SELECT json_object(...)`, which is why the engine ships `UnsupportedOperationException` for
  BigQuery, Databricks and Trino.
- **Don't take the `CREATE ALIAS` exit** (§4.2). It closes every remaining gap by running Java inside
  the database.
- **Don't make golden text binding corpus-wide** (§6), and don't reach for normalization — the
  ceiling is ~6%.
- **Don't make `EngineStyleH2` the execution dialect.** Its output is byte-pinned to goldens.
- **Don't create a soft `h2-divergence` bucket** (§10).
